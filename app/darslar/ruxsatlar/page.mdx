eshik qulfi va seyf — har biri boshqasi o‘tkazib yuborgan narsani ushlaydi.

Claude Code’da ham uch qatlam bor:

| Qatlam | Savol | Kim ijro etadi |
| --- | --- | --- |
| **Rejim** | Agent har harakatda so‘raydimi yoki o‘zi qaror qiladimi? | Claude Code |

## 3. Olti rejim

Oddiy tilda: rejim — agentga beriladigan **mustaqillik darajasi**.
Yangi stajyor har qadamni so‘raydi; ishonchli hamkasb mayda narsalarni
o‘zi hal qiladi; konteyner ichidagi robot esa umuman so‘ramaydi.

| Rejim (sozlama qiymati) | Interfeysda | So‘rovsiz nima ishlaydi |
| --- | --- | --- |
| `default` | Manual | Faqat o‘qish |
| `acceptEdits` | Accept edits | O‘qish, fayl tahrirlari va ish papkasida `mkdir`, `touch`, `rm`, `rmdir`, `mv`, `cp`, `sed` |
| `plan` | Plan | O‘qish; tahrir — reja tasdiqlanguncha yo‘q |
| `auto` | Auto | Hammasi, lekin fon klassifikatori xavfli harakatni to‘xtatadi |
| `dontAsk` | Don’t ask | Faqat oldindan ruxsat berilganlar; so‘raladigan hamma narsa **rad** etiladi |
| `bypassPermissions` | Bypass | Deyarli hammasi, tekshiruvlarsiz |

### 3.1 Qaysi rejimda boshlanadi

Hujjatga ko‘ra yangi versiyalarda (v2.1.283 dan) interaktiv terminal va VS
Code sessiyasi standart holatda **auto** rejimda ochiladi. Boshqa rejimni
tanlash:

- bir sessiya uchun: `claude --permission-mode default` (yoki `plan`,
  `acceptEdits`...);
- doimiy: sozlamada `permissions.defaultMode`;
- sessiya ichida: **`Shift+Tab`**.

`Shift+Tab` aylanishi: auto’dan birinchi bosish — Manual’ga, keyin
**Manual → Accept edits → Plan**, keyin yoqilgan bo‘lsa Bypass va Auto.
`dontAsk` aylanishda yo‘q — faqat `--permission-mode dontAsk` bilan.

<Callout type="ogoh" title="Loyiha fayli auto va bypass'ni yoqa olmaydi">
Hujjatga ko‘ra `"auto"` va `"bypassPermissions"` ni `.claude/settings.json`
yoki `.claude/settings.local.json` da `defaultMode` qilib qo‘ysangiz —
**ishlamaydi**. Bu himoya: begona repo klon qilinganda u sizni o‘zi
xavfli rejimga o‘tkaza olmaydi. Ularni faqat foydalanuvchi sozlamasida yoki
bayroq bilan yoqasiz.
</Callout>

### 3.2 Qaysi rejim qachon

| Vaziyat | Rejim |
| --- | --- |
| Birinchi hafta, notanish loyiha, muhim tizim | **Manual** — har harakatni ko‘rasiz |
| Katta o‘zgarishdan oldin o‘rganish | **Plan** |
| Ishonchli loyihada kundalik kodlash | **Accept edits** yoki **Auto** |
| CI, skript, kuzatuvsiz ish | **dontAsk** + aniq allow ro‘yxati (15-dars) |
| Internetsiz konteyner yoki VM ichida | **bypassPermissions** — faqat shu yerda |

## 4. Plan rejimi: avval o‘ylash

Oddiy tilda: ta’mirchi devorni buzishdan oldin chizma ko‘rsatadi. Siz
“ma’qul” demaguningizcha u bolg‘a olmaydi.

Plan rejimida Claude kodni o‘qiydi va o‘rganadi, lekin **reja
tasdiqlanmaguncha tahrir qilmaydi**. Kirish: `Shift+Tab`, so‘rov boshida
`/plan` yoki `--permission-mode plan`.

Reja tayyor bo‘lganda uch tanlov chiqadi:

1. **Ha, va auto rejimga o‘t** — reja bo‘yicha mustaqil ishlaydi;
2. **Ha, tahrirlarni qo‘lda tasdiqlayman** — Manual’da bajaradi;
3. **Yo‘q, rejalashtirishni davom ettir.**

Rejani tasdiqlashdan oldin **`Ctrl+G`** bilan uni matn muharririda
ochib, o‘zingiz tahrirlashingiz mumkin: keraksiz qadamni o‘chirish,
cheklov qo‘shish. Plan rejimi qachon kerakligi va qachon ortiqcha — 6-dars.

## 5. Auto rejimi: klassifikator

Oddiy tilda: auto rejimda har harakatni siz emas, **ikkinchi model** —
klassifikator — ko‘rib chiqadi. U navbatchi xavfsizlik xodimiga o‘xshaydi:
oddiy ishlarni o‘tkazib yuboradi, shubhalisini to‘xtatadi.

Hujjatga ko‘ra klassifikator so‘ralgandan **ortiq** narsani, notanish
infratuzilmaga qaratilgan harakatni yoki Claude o‘qigan zararli kontent
ta’sirida paydo bo‘lgandek ko‘ringan harakatni bloklaydi. Standart
holatda bloklanadiganlarga misollar: `curl | bash`, majburiy push
(force push), `git reset --hard`, `terraform destroy`, production deploy.
To‘liq ro‘yxat: `claude auto-mode defaults`.

Uchta muhim tafsilot:

- **Keng qoidalar tashlab yuboriladi.** Auto rejimga kirganda `Bash(*)`,
  `Bash(python*)` kabi interpretator yulduzchalari va paket menejer
  “run” buyruqlari kabi keng allow qoidalari o‘chadi. `Bash(npm test)`
  kabi tor qoidalar qoladi.
- **To‘xtash chegarasi.** Ketma-ket 3 ta yoki sessiyada jami 20 ta
  bloklashdan keyin auto pauza qiladi va yana sizdan so‘ray boshlaydi.
- **Kafolat emas.** Hujjat so‘zlari bilan: auto rejimi so‘rovlarni
  kamaytiradi, lekin **xavfsizlikni kafolatlamaydi**.

<Check q="Auto rejimda Bash(python *) allow qoidangiz ishlamayapti — har python buyrug'i klassifikatordan o'tyapti. Nega?">
Hujjatga ko‘ra auto rejimga kirishda interpretator yulduzchalari
(`Bash(python*)` kabi) va boshqa keng allow qoidalari tashlab yuboriladi —
ular ixtiyoriy kodni ishga tushirishga ruxsat beradi. Tor qoidalar
(`Bash(python -m unittest *)`) saqlanadi.
</Check>

## 6. dontAsk va bypassPermissions

**`dontAsk`** — kuzatuvsiz ish uchun: so‘rov chiqishi kerak bo‘lgan har
qanday harakat **avtomatik rad etiladi**. Ishlaydi faqat: ish
papkasidagi o‘qish, faqat-o‘qish Bash buyruqlari va allow qoidalariga
mos kelganlar. CI’da aniq allow ro‘yxati bilan birga ishlatiladi (15-dars).

**`bypassPermissions`** — so‘rovlar va xavfsizlik tekshiruvlari o‘chadi,
himoyalangan yo‘llarga yozish ham. Deny qoidalari baribir ishlaydi.
Hujjatdagi ogohlantirishlar:

- faqat **konteyner, VM yoki internetsiz dev konteyner** kabi izolyatsiya
  qilingan muhitda ishlating, Claude Code asosiy tizimingizga zarar
  yetkaza olmaydigan joyda;
- bu rejim **prompt injection** va kutilmagan harakatlardan hech qanday
  himoya bermaydi;
- `--dangerously-skip-permissions` — xuddi shu rejim; root yoki sudo
  bilan ishlamaydi.

<Callout type="xato" title="Klassik xato">
“So‘rovlar zeriktirdi” deb shaxsiy noutbukda `--dangerously-skip-permissions`
bilan ishlash. Bitta noto‘g‘ri buyruq yoki o‘qilgan sahifadagi yashirin
ko‘rsatma — va agent sizning to‘liq huquqlaringiz bilan ishlaydi. So‘rovlarni
kamaytirishning to‘g‘ri yo‘li — aniq allow qoidalari va sandbox (15-bo‘lim).
</Callout>

## 7. Qoidalar: allow, ask, deny

Oddiy tilda: uchta ro‘yxat. **Allow** — so‘rovsiz bajar. **Ask** — har
doim mendan so‘ra. **Deny** — hech qachon.

```json
{
  "permissions": {
    "allow": ["Bash(npm run test *)", "Edit(./src/**)"],
    "ask": ["Bash(git commit *)"],
    "deny": ["Bash(git push *)", "Read(./.env)"]
  }
}
```

Qoida ko‘rinishi: `Asbob` yoki `Asbob(aniqlovchi)`. Asbob nomlari — 1-darsdagi
nomlar: `Bash`, `Read`, `Edit`, `WebFetch`, `Agent`...

### 7.1 Tekshirish tartibi

Hujjatdagi asosiy qoida: **avval deny, keyin ask, keyin allow. Shu
tartibdagi birinchi moslik qaror qiladi, va aniqlik (specificity) tartibni
o‘zgartirmaydi.**

<Flow nodes={["Harakat", "Deny'ga mosmi? → taqiqlangan", "Ask'ga mosmi? → so'raladi", "Allow'ga mosmi? → so'rovsiz", "Hech biriga mos emas → rejimning standart xulqi"]} caption="Tartib hech qachon o'zgarmaydi: deny har doim birinchi." />

Bundan uchta oqibat:

1. **Deny’dan istisno yo‘q.** `Bash(aws *)` deny bo‘lsa, `Bash(aws s3 ls)`
   allow uni ochmaydi. Hujjat: allow qoidasi deny’dan istisno o‘yib chiqara
   olmaydi.
2. **Ask aniqroq allow’dan ham kuchli.** `Bash(npm test *)` allow va
   `Bash(npm test --update *)` ask bo‘lsa — `npm test --update x` so‘raladi.
3. **Yalang‘och asbob nomi deny’da** (masalan, `"Bash"`) asbobni Claude
   kontekstidan **butunlay olib tashlaydi**.

### 7.2 Hech narsaga mos kelmasa

Manual rejimda: ish papkasidagi o‘qish — so‘rovsiz; papkadan tashqari
o‘qish, fayl tahriri, faqat-o‘qish bo‘lmagan Bash va veb so‘rovlari —
so‘raladi. Bash uchun hujjat buni “fail-closed” deb ataydi: mos qoida
bo‘lmasa, tasdiq kerak.

## 8. Bash qoidalari qanday mos keladi

Bash qoidalari eng ko‘p ishlatiladi va eng ko‘p xato qilinadi.

### 8.1 Yulduzcha

- Yulduzchasiz qoida — **aynan bitta** buyruq: `Bash(npm run build)`.
- `*` — istalgan matn (bo‘sh joylar bilan ham), istalgan joyda.
- **Bo‘sh joy muhim:** `Bash(ls *)` → `ls` va `ls -la`, lekin `lsof` emas.
  `Bash(ls*)` → `lsof` ham.
- `Bash(ls:*)` — `Bash(ls *)` ning boshqacha yozilishi.
- `*` ni subbuyruqdan **keyin** qo‘ying: `Bash(git log *)`, `Bash(git *)` emas.

| Qoida | Mos keladi | Mos kelmaydi |
| --- | --- | --- |
| `Bash(npm run *)` | `npm run test --watch`, `npm run` | `npm install` |
| `Bash(git push *)` | `git push`, `git push --force origin main` | `git -C . push` |
| `Bash(rm -rf *)` | `rm -rf build` | `rm -r -f build` |
| `Bash(npm run build)` | `npm run build` | `npm run build --prod` |

### 8.2 Murakkab buyruqlar

`&&`, `||`, `;`, `|`, `&` va yangi qator bilan bog‘langan buyruqlar
**qismlarga bo‘linadi** va har qism alohida tekshiriladi. Deny yoki ask
istalgan qismga mos kelsa — butun buyruq uchun amal qiladi (`$(...)`
ichida ham). Hujjat: qoida **har bir qismga alohida** mos kelishi kerak —
ya’ni `npm test && npm publish` faqat ikkala qism ham ruxsat etilganda
so‘rovsiz o‘tadi.

### 8.3 O‘ramlar va o‘zgaruvchilar

- Moslashdan oldin `timeout`, `time`, `nice`, `nohup`, `stdbuf`,
  `command`, `builtin`, `noglob` va yalang‘och `xargs` olib tashlanadi:
  `timeout 60 git push` → `git push` deny’ga tushadi.
- `npx`, `docker exec`, `direnv exec` kabi ishga tushirgichlar olib
  **tashlanmaydi**.
- Boshidagi `FOO=bar` kabi o‘zgaruvchilar: deny va ask ulardan o‘tib
  moslashadi (`FOO=bar rm -rf tmp/` → `Bash(rm *)` deny); allow esa faqat
  ma’lum xavfsiz o‘zgaruvchilardan (masalan `NODE_ENV`) o‘tadi.

### 8.4 So‘rovsiz o‘qish buyruqlari

`ls`, `cat`, `echo`, `pwd`, `head`, `tail`, `grep`, `find`, `wc`,
`which`, `diff`, `stat`, `du`, `cd` va faqat o‘qiydigan `git` buyruqlari
har rejimda so‘rovsiz ishlaydi — ular uchun allow yozish shart emas.
Ro‘yxatni sozlab bo‘lmaydi; birortasini so‘ratmoqchi bo‘lsangiz, ask yoki
deny qoidasi qo‘shasiz.

## 9. Bash qoidalari xavfsizlik chegarasi emas

Bu — darsning eng muhim bo‘limi.

Oddiy tilda: eshik qulfini qo‘ydingiz, lekin deraza ochiq qolgan.
`Bash(git push *)` deny — eshik qulfi. U Claude **odatda** yozadigan
buyruqni to‘xtatadi. Lekin xuddi shu dasturni boshqa yo‘l bilan
chaqirish mumkin.

Hujjat buni ochiq aytadi: Bash qoidasi dasturni **boshqa shaklda**
chaqirishga mos kelmaydi, shuning uchun deny yoki ask qoidasi Claude odatda
yozadigan chaqiruvni qamraydi va **dastur atrofidagi xavfsizlik chegarasi
emas**.

| Qoida | Aylanib o‘tish yo‘li |
| --- | --- |
| `Bash(git push *)` deny | `git -C . push`, `git -c x=y push` |
| `Bash(curl *)` deny | `/usr/bin/curl ...`, `sh -c 'curl ...'` |
| `Bash(./deploy.sh *)` deny | `sh deploy.sh`, `bash ./deploy.sh` |
| `Read(./.env)` deny | `python -c "print(open('.env').read())"`, `grep -r PAROL .` |

Amaliyotdagi `tekshir.py` oxirida aynan shunday holatlar ko‘rsatiladi.

**Nima qilish kerak:** Bash qoidalari — **qulaylik va birinchi to‘siq**
uchun. Haqiqiy chegara kerak bo‘lsa — **sandbox** (14-bo‘lim) va
**hooks** (12-dars). Hujjatning tavsiyasi: ikkalasini birga ishlating —
prompt injection Claude qarorini chetlab o‘tsa ham, sandbox cheklovlari
baribir turadi.

<Check q="Siz Bash(curl *) ni deny qildingiz va endi tarmoq xavfsiz deb hisoblaysiz. Nima xato?">
Bu qoida faqat `curl ...` ko‘rinishidagi chaqiruvni to‘xtatadi.
`/usr/bin/curl`, `sh -c 'curl ...'`, `wget`, Python yoki Node skripti
orqali so‘rov — bularning hech biri mos kelmaydi. Hujjat: Bash qoidalari
xavfsizlik chegarasi emas. Tarmoqni haqiqatan cheklash uchun sandbox’ning
tarmoq allowlist’i kerak.
</Check>

## 10. Fayl qoidalari: Read va Edit

Oddiy tilda: fayl qoidalari — “qaysi papkaga kirish mumkin” ro‘yxati.
Ular `.gitignore` sintaksisida yoziladi.

| Yozilishi | Ma’nosi |
| --- | --- |
| `//etc/hosts` | Mutlaq yo‘l |
| `~/.ssh/**` | Uy papkasiga nisbatan |
| `/config/**` | Sozlama manbasiga nisbatan (loyiha sozlamasida — loyiha ildizi) |
| `./src/**` yoki `src/**` | Joriy papkaga nisbatan |
| `*` | Bitta papka ichida |
| `**` | Istalgan chuqurlikda |

Hujjatdagi muhim tafsilotlar:

- `.env` va `**/.env` — bir xil: **istalgan chuqurlikdagi** `.env`.
  Aniqlik uchun `Read(**/.env)` deb yozish qulay.
- **`Edit` qoidalari fayl tahrirlaydigan barcha o‘rnatilgan asboblarga**
  amal qiladi. `Write(...)` deb alohida yozish kerak emas.
- **`Read` deny tahrirni ham bloklaydi** — o‘sha yo‘lda `Edit` va `Write`
  ham, yangi fayl yaratish ham taqiqlanadi.
- Read va Edit deny **Bash’dagi taniqli fayl buyruqlariga** ham amal qiladi:
  `cat`, `head`, `tail`, `sed`, `tee` va `>` yo‘naltirish nishonlari.
  `cat .env` → taqiqlangan.
- Lekin **faylni nomlamasdan o‘qiydigan** buyruqlarga (`grep -r pattern .`)
  va faylni o‘zi ochadigan skriptlarga (Python, Node) amal **qilmaydi**.
- **`.claudeignore` ning hech qanday ta’siri yo‘q.** Eski qo‘llanmalarda
  uchraydi — uning o‘rniga `Read` deny qoidalari.

<Callout type="ogoh" title="Sirlarni himoyalash retsepti">
`Read(**/.env)` va `Read(./secrets/**)` deny — birinchi qatlam. Lekin 9-bo‘lim
sababli bu yetarli emas: sandbox’da `filesystem.denyRead` bilan o‘sha
yo‘llarni OS darajasida yoping. Eng yaxshisi — haqiqiy production sirlarini
umuman ish kompyuteridagi loyiha papkasida saqlamaslik.
</Callout>

## 11. Veb va boshqa asboblar

- **`WebFetch(domain:docs.python.org)`** — aniq domen.
  `WebFetch(domain:*.example.com)` — istalgan subdomen (lekin
  `example.com` ning o‘zi emas). `domain:*` — hammasi.
- Hujjatdagi ogohlantirish: **faqat WebFetch’ni cheklash tarmoqni
  cheklamaydi** — Bash ruxsat etilgan bo‘lsa, Claude `curl`, `wget` va
  boshqa vositalar bilan istalgan manzilga chiqa oladi.
- **MCP:** `mcp__github` (butun server), `mcp__github__*`, yoki aniq asbob
  `mcp__github__create_issue` (13-dars).
- **Subagentlar:** `Agent(Explore)`, `Agent(my-agent)` (11-dars).

## 12. Qoidalar qayerda yashaydi

2-darsdagi fayllar xaritasini eslang. Ruxsat qoidalari shu fayllarning
`permissions` qismida turadi:

| Fayl | Kimga | Kim ko‘radi |
| --- | --- | --- |
| Tashkilot (managed) sozlamasi | Butun tashkilot | Administrator boshqaradi |
| `--settings` bayrog‘i | Bir ishga tushirish | — |
| `.claude/settings.local.json` | Siz, shu loyihada | Faqat siz |
| `.claude/settings.json` | Jamoa, shu loyihada | Git orqali hamma |
| `~/.claude/settings.json` | Siz, hamma loyihada | Faqat siz |

Ikkita qoida hujjatdan:

- **Ro‘yxatlar birlashadi.** `permissions.allow` bir nechta faylda bo‘lsa,
  Claude Code ularni **qo‘shib** ishlatadi — birini tanlamaydi.
  `defaultMode` kabi yagona qiymatlarda esa eng yuqori daraja yutadi.
- **Istalgan darajadagi deny ustun.** Foydalanuvchi sozlamasi allow qilsa-yu,
  loyiha deny qilsa — taqiqlanadi; va aksincha. Tashkilot deny’ini hech
  narsa ochmaydi.

Yana ikki amaliy tafsilot:

- **“Ha, va boshqa so‘rama”** tugmasi Bash va WebFetch uchun qoidani

## 14. Sandbox: operatsion tizim devori

Oddiy tilda: qoidalar — qorovulning ro‘yxati. Sandbox — binoning o‘zi:
devorlar va eshiklar. Qorovulni aldash mumkin, devordan o‘tib bo‘lmaydi.

### 14.1 Nima qiladi

Sandbox **Bash** (va PowerShell, Monitor) buyruqlari hamda ular ishga
tushirgan jarayonlarni OS darajasida cheklaydi:

- **Fayllar:** yozish — standart holatda faqat ish papkasi, vaqtinchalik
  papka va qo‘shilgan papkalar. O‘qish — kompyuterning ko‘p qismi (`~/.ssh`
  ham!), agar `denyRead` bilan yopmasangiz.
- **Tarmoq:** to‘g‘ridan-to‘g‘ri yo‘l yo‘q; har so‘rov proksi orqali
  domen bo‘yicha tekshiriladi. Ruxsat etilgan domenlar boshida **bo‘sh**.

Qamramaydi: Claude’ning `Read`, `Edit`, `Write` asboblari, WebFetch, MCP
serverlari va hooks — ular ruxsat qoidalari bilan boshqariladi.

### 14.2 Qayerda ishlaydi va qanday yoqiladi

| Tizim | Holat |
| --- | --- |
| macOS | Ishlaydi (Seatbelt) |
| Linux, WSL 2 | Ishlaydi (bubblewrap + socat) |
| Native Windows | **Yo‘q** — buyruqlar sandbox’siz |

Yoqish: sessiyada **`/sandbox`** yoki sozlamada `"sandbox": {"enabled": true}`.
Standart holatda o‘chiq. Muhim: hujjatga ko‘ra sandbox ishga tusha olmasa
(paket yetishmasa), Claude Code **sandbox’siz davom etadi** —
`"failIfUnavailable": true` bilan buning o‘rniga to‘xtaydi.

### 14.3 Asosiy sozlamalar

```json
{
  "sandbox": {
    "enabled": true,
    "failIfUnavailable": true,
    "allowUnsandboxedCommands": false,
    "filesystem": {
      "denyRead": ["~/.ssh", "~/.aws"],
      "allowWrite": ["/tmp/build"]
    },
    "network": {
      "allowedDomains": ["pypi.org", "files.pythonhosted.org"]
    }
  }
}
```

| Kalit | Nima qiladi |
| --- | --- |
| `autoAllowBashIfSandboxed` | Sandbox’dagi buyruqlar so‘rovsiz (standart `true`); deny qoidalari baribir ishlaydi |
| `allowUnsandboxedCommands` | Claude buyruqni sandbox’dan **tashqarida** qayta urinishiga ruxsat (standart `true`); `false` — bu yo‘l yopiladi |
| `excludedCommands` | Sandbox’dan chiqarib qo‘yiladigan buyruqlar — ular **to‘liq huquqingiz** bilan ishlaydi |
| `network.allowedDomains` / `deniedDomains` | Tarmoq oq va qora ro‘yxati |
| `filesystem.denyRead` / `allowWrite` | Qo‘shimcha o‘qish taqiqlari va yozish ruxsatlari |

### 14.4 Cheklovlari

Hujjat halol: sandbox **xavfni kamaytiradi, lekin to‘liq izolyatsiya
chegarasi emas**. Va: samarali sandbox uchun **fayl tizimi ham, tarmoq
ham** cheklangan bo‘lishi kerak — faqat bittasi yetarli emas. Proksi
o‘zgaruvchilarini e’tiborsiz qoldiradigan vositalar (oddiy `ssh`, ko‘p
baza drayverlari) ruxsat etilgan hostga ham ulana olmaydi — buni bilib
qo‘ying.

<Check q="Sandbox yoqilgan, lekin network.allowedDomains bo'sh. Agent pip install qilmoqchi. Nima bo'ladi?">
Tarmoq proksi orqali tekshiriladi va ro‘yxatda bo‘lmagan host uchun Manual
va Accept edits rejimlarida so‘rov chiqadi (auto’da rad etiladi, agar
oldindan tasdiqlanmagan bo‘lsa; dontAsk’da rad etiladi). Doimiy yechim —
`pypi.org` va `files.pythonhosted.org` ni `allowedDomains` ga qo‘shish.
</Check>

## 15. Jamoa uchun tayyor sozlama

Oddiy tilda: hamma qatlamni birlashtiramiz. Quyidagi namuna — o‘rtacha
Python loyihasi uchun boshlang‘ich nuqta. Uni o‘z loyihangizga moslang.

```json
{
  "permissions": {
    "allow": [
      "Bash(python -m pytest *)",
      "Bash(ruff check *)",
      "Bash(ruff format *)",
      "Edit(./src/**)",
      "Edit(./tests/**)"
    ],
    "ask": [
      "Bash(git commit *)",
      "Bash(pip install *)",
      "Edit(./migrations/**)"
    ],
    "deny": [
      "Bash(git push *)",
      "Bash(rm -rf *)",
      "Read(**/.env)",
      "Read(./secrets/**)"
    ]
  },
  "sandbox": {
    "enabled": true,
    "network": {
      "allowedDomains": ["pypi.org", "files.pythonhosted.org", "docs.python.org"]
    },
    "filesystem": {
      "denyRead": ["~/.ssh", "~/.aws"]
    }
  }
}
```

Bu sozlamaning mantig‘i:

- **Allow** — faqat **tor** va tez-tez kerak bo‘ladigan buyruqlar: test,
  lint, kod papkalari. Interpretator yulduzchasi (`Bash(python *)`) yo‘q.
- **Ask** — qaytarib bo‘lmaydigan yoki tashqariga ta’sir qiladigan, lekin
  ba’zan kerak bo‘ladigan narsalar.
- **Deny** — hech qachon kerak bo‘lmaydigan narsalar. Ular **birinchi
  to‘siq**, chegara emas.
- **Sandbox** — haqiqiy chegara: tarmoq faqat kerakli domenlarga, sirli
  papkalar yopiq.

Bu fayl `.claude/settings.json` sifatida commit qilinadi — butun jamoa
bir xil qoidalar bilan ishlaydi. Shaxsiy qo‘shimchalar —
`.claude/settings.local.json` da.

## 19. Nazorat savollari

<QA q="Ruxsat qoidalari qanday tartibda tekshiriladi va 'aniqroq qoida yutadi' degan gap to'g'rimi?">
Deny, keyin ask, keyin allow; shu tartibdagi birinchi moslik qaror qiladi.
Aniqlik tartibni o‘zgartirmaydi: `Bash(aws *)` deny bo‘lsa, `Bash(aws s3
ls)` allow uni ochmaydi.
</QA>

<QA q="Bash(ls *) va Bash(ls*) ning farqi nima?">
`Bash(ls *)` — `ls` va `ls -la` ga mos, `lsof` ga emas (bo‘sh joy so‘z
chegarasini belgilaydi). `Bash(ls*)` — `lsof` ga ham mos.
</QA>

<QA q="npm test && npm publish buyrug'i qachon so'rovsiz o'tadi?">
Faqat ikkala qism ham alohida ruxsat etilgan bo‘lsa (allow qoidasi yoki
faqat-o‘qish buyrug‘i). Hujjat: qoida har bir qismga alohida mos kelishi
kerak. Qismlardan biri deny’ga tushsa — butun buyruq taqiqlanadi.
</QA>

<QA q="Nega Bash qoidalari xavfsizlik chegarasi emas? Ikki misol keltiring.">
Ular Claude odatda yozadigan chaqiruvni qamraydi, dasturning o‘zini emas.
`Bash(git push *)` deny `git -C . push` ni to‘xtatmaydi; `Bash(curl *)` deny
`/usr/bin/curl` yoki `sh -c 'curl ...'` ni to‘xtatmaydi. Chegara uchun —
sandbox va hooks.
</QA>

<QA q="Read(**/.env) deny qaysi holatlarda sirni himoya qiladi va qaysilarida yo'q?">
Himoya qiladi: Claude’ning Read asbobi, Edit/Write (Read deny tahrirni
ham bloklaydi), `cat`, `head`, `tail`, `sed`, `tee` va yo‘naltirishlar.
Himoya qilmaydi: faylni nomlamasdan o‘qiydigan `grep -r ... .` va faylni
o‘zi ochadigan Python yoki Node skripti. Ularga qarshi — sandbox
`denyRead`.
</QA>

<QA q="Foydalanuvchi sozlamasida Bash(git *) allow, loyihada Bash(git push *) deny. Push nima bo'ladi?">
Taqiqlanadi. Ro‘yxatlar birlashadi va deny har doim birinchi tekshiriladi;
istalgan darajadagi deny ustun.
</QA>

<QA q="Loyihaning .claude/settings.json fayliga defaultMode: bypassPermissions yozildi. Nima bo'ladi?">
Hech narsa: hujjatga ko‘ra auto va bypassPermissions loyiha va local
sozlamalarida `defaultMode` sifatida ishlamaydi. Bu begona repo sizni
xavfli rejimga o‘tkaza olmasligi uchun.
</QA>

<QA q="Auto rejim bilan Manual rejimning asosiy farqi nima va auto qachon to'xtaydi?">
Manual’da xavfli harakatlarni siz tasdiqlaysiz; auto’da ikkinchi model —
klassifikator — qaror qiladi. Ketma-ket 3 yoki jami 20 bloklashdan keyin
auto pauza qilib, yana so‘ray boshlaydi.
</QA>

<QA q="Sandbox nimani cheklaydi va nimani cheklamaydi?">
Cheklaydi: Bash (va PowerShell, Monitor) buyruqlari va ularning
jarayonlari — fayllarga yozish/o‘qish va tarmoq. Cheklamaydi: Claude’ning
Read/Edit/Write asboblari, WebFetch, MCP serverlari, hooks — ular ruxsat
qoidalari bilan boshqariladi.
</QA>

<QA q="Sandbox o'rnatilgan, lekin bubblewrap paketi yo'q. Nima bo'ladi va buni qanday oldini olasiz?">
Hujjatga ko‘ra standart holatda Claude Code buyruqlarni sandbox’siz
ishlatishda davom etadi. Buni oldini olish uchun `sandbox.failIfUnavailable:
true` — sandbox ishga tushmasa, Claude Code to‘xtaydi.
</QA>

<QA q="'Ha, va boshqa so'rama' bosilganda qoida qayerga yoziladi?">
Bash va WebFetch uchun — git repo ildizidagi `.claude/settings.local.json`
ga. Fayl tahriri ruxsatlari esa faylga saqlanmaydi, sessiya oxirigacha
amal qiladi.
</QA>
